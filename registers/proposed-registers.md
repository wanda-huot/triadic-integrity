## 1. Purpose

This file collects possible future **Human Registers** for The Triadic Integrity Framework.

A Human Register is a Layer 2 translation layer: a way of speaking the same underlying structure for a particular audience, domain, or situation.

Proposed registers are not yet canonical.

They are candidates.

This file exists so that promising register ideas can be saved without cluttering the core framework files.

## 9. Bridges are separate from Human Registers

Some possible future materials are not Human Registers.

They are **Bridges**.

A Bridge is a comparative translation document that connects The Triadic Integrity Framework with an external framework, theory, tradition, modality, or vocabulary.

Human Registers translate the framework into usable language for a domain or audience.

Bridges translate between the framework and an external system.

Key distinction:

```text
Human Registers = how the framework speaks.
Bridges = how the framework compares and translates across systems.
Expression Formats = how the framework appears, circulates, and operates.
```

See:

```text
bridges/README.md
```

## 12. Promotion criteria for a Human Register

A proposed register can become a full register file when it has:

```text
1. A clear name
2. A clear audience or domain
3. A core translation table
4. Definitions for the translated terms
5. Diagnostic translations for Slack, Tight, Misdirected, and Coherent Formation
6. At least one practical example
7. A traceability table back to Layer 1 and Layer 0
```

Suggested file pattern:

```text
registers/[name]-register.md
```

Examples:

```text
registers/relational-register.md
registers/narrative-register.md
registers/creative-practice-register.md
registers/cognitive-register.md
```

---

## 13. Promotion criteria for a Bridge

A proposed Bridge can become a full Bridge file when it has:

```text
1. A clear external system being compared
2. A careful summary of that external system
3. A translation table
4. Useful resonances
5. Mismatches and limits
6. What not to claim
7. A clear explanation of what the comparison helps us see
```

Suggested file pattern:

```text
bridges/[external-system]-bridge.md
```

Examples:

```text
bridges/peirce-bridge.md
bridges/active-inference-bridge.md
bridges/four-e-cognition-bridge.md
bridges/act-bridge.md
```

## 14. Development priority

The framework should grow vertically before it grows horizontally.

This means:

- deepen one register before adding many more
- add worked examples before adding more vocabulary
- test whether a register actually helps
- avoid creating registers just because a domain sounds interesting
- keep Bridge work separate from Human Register work
- keep Expression Formats separate from both

The next best development step is probably not another long list.

It is a small number of worked examples that show how the current registers function in practice.

---

## 15. Working rule

When considering a new Human Register, ask:

```text
Who is this language for?
What does it help them notice?
What does it help them do?
Does it map cleanly back to Layer 1?
Does it preserve the Layer 0 structure?
Does it add real usability, or only new names?
```

When considering a new Bridge, ask:

```text
What external system is being compared?
What translates cleanly?
What only loosely resonates?
Where does the comparison break?
What should not be claimed?
What does this comparison help us see?
```

A register should earn its place by making the framework more usable.

A Bridge should earn its place by making comparison clearer.
